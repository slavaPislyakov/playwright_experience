# 20 полезных скиллов/рулов для программиста

Составлено по итогам реальной работы: каждое «зачем» — либо уже пережитый кейс в этом репозитории, либо типовой цикл, который повторяется у любого разработчика. Три из списка уже существуют: `git-commit`, `review-changes` (глобальные, `~/.zcode/skills/`), `write-autotests` (проектный).

## Уроки, на которых построены эти идеи

Из наших двух скиллов вырисовываются признаки хорошего скилла: **напористый description** с конкретными фразами-триггерами (иначе не триггерится); **дефолт + переопределение аргументом**, а не вопросы каждый раз; **правила безопасности** (что никогда не делать без спроса); **дословный пример формата** результата вместо абстрактных требований; **правила доказательности** («не выдумывай находки», «гипотеза ≠ факт»).

## Git и история

### 1. git-commit — уже есть ✅
Коммит по официальным гайдлайнам git: тема ≤50, императив, тело «why», разбивка несвязанного. Опыт показал ценность правил безопасности: не стейджить секреты, не push/amend без спроса, не `--no-verify`.

### 2. pr-description
**Что:** по диффу ветки против master собирает описание PR: самари, мотивация, риски, чек-лист проверки, скриншоты/артефакты.
**Зачем:** тот же разбор диффа, что в `review-changes`, но на выходе — документ для ревьюеров, а не отчёт себе. Пары «git-commit + review-changes» не хватает ровно этого звена.

### 3. split-commits
**Что:** находит в свалке незакоммиченных изменений логические группы и предлагает план из N коммитов с готовыми сообщениями; применяет только после подтверждения.
**Зачем:** мы делали это вручную дважды (правила агента + чистка доков). Автоматизируется целиком.

## Качество кода

### 4. review-changes — уже есть ✅
Самари + гейты фактами + узкие места P0–P3 с решениями. Ключевое правило, которое стоит перенести во все скиллы: «узких мест нет — валидный ответ».

### 5. lint-audit — «линтер точно работает?»
**Что:** подкладывает в репозиторий файлы с заранее известными нарушениями и проверяет, что линтер их ловит; сверяет активные правила со стеком; предлагает добавить/убрать.
**Зачем:** мы нашли 3 реальных недочёта конфига только потому, что проверили линтер пробами, а не поверили `npm run lint`. Универсальный приём для ESLint/ruff/prettier любого проекта.

### 6. dead-code-scan
**Что:** ищет неиспользуемые экспорты, файлы, переменные окружения, зависимости; отчёт с планом удаления.
**Зачем:** в этом репо нашлись легаси `BASE_URL_AUTH` от удалённого hockey-клиента и PO/степы registrationModal, которые не покрыты ни одним тестом. Такой скан дешёв и сразу даёт работу.

### 7. refactor-staged
**Что:** большой рефакторинг режет на этапы с фиксированным порядком: план → этап → гейты (typecheck/lint/tests) → следующий этап. Один этап за раз, тесты не гонять в промежуточном состоянии.
**Зачем:** наш typescript-refactoring (stages 1–6) и кампания пакетов прошли именно так; формула «агенты в фоне на непересекающихся файлах + один централизованный прогон» уже доказана в этом репо.

### 8. conventions-sync
**Что:** после крупных изменений (удаление файлов, смена пайплайна) сверяет AGENTS.md, README и скиллы с фактическим состоянием репозитория, чинит висячие ссылки.
**Зачем:** после удаления корневых доков мы руками вычищали 6 ссылок. Доки протухают незаметно — это систематический обход.

## Тестирование

### 9. coverage-gaps
**Что:** сопоставляет тестируемую поверхность (эндпоинты API, страницы и компоненты UI) с существующими тестами; выдаёт приоритизированный роадмап с оценкой усилий.
**Зачем:** наш анализ «36 API + 11 UI тестов, CRUD-паритет, мёртвые PO» — ровно этот скилл. Хочется повторять после каждого большого релиза продукта.

### 10. flaky-hunter
**Что:** гоняет подозрительный тест N раз (локально или `--retries`), классифицирует причины (таймауты, динамический контент, порядок тестов, внешние сервисы), предлагает фикс из каталога решений.
**Зачем:** live-site тесты rabota.by флакают; мы уже накопили каталог решений (allowlist JS-шума, aria-снапшоты вместо пиксель-диффов, domcontentloaded вместо load) — он должен подсказывать сам.

### 11. regression-on-bug
**Что:** жёсткий ритуал «баг → фикс»: сначала падающий тест, воспроизводящий баг, потом фикс, потом зелёный прогон. Запрещает фикс без теста.
**Зачем:** это уже правило вашего AGENTS.md («для исправления бага добавляй регрессионный тест») — но правило без процедуры не исполняется, а скилл даёт процедуру.

### 12. test-data-builder
**Что:** по типам запросов ресурса генерит builder-классы: валидный дефолт + fluent `with*` + `without()` для негативных кейсов; регистрирует в фикстурах.
**Зачем:** мы построили три билдера руками (post/album/todo) и открыли вопрос `postRaw` — шаблон готов к автоматизации, и он нужен в любом API-проекте.

## Зависимости и апгрейды

### 13. dependency-upgrade
**Что:** staged-кампания обновления пакетов: аудит breaking changes под конкретный код → этапы (рантайм → линтер → типы → фреймворк) → гейты после каждого этапа → отчёт «что не обновлено и почему».
**Зачем:** кампания ESLint 9→10 + Playwright 1.60→1.65 + TS-блокеры — образцовый кейс: без этапности и гейтов это был бы день дебага вперемешку.

### 14. release-notes-digest
**Что:** читает changelog/release notes фреймворка между текущей и целевой версией; выдаёт «брать / не брать / проверить под наш код» с обоснованием.
**Зачем:** наш разбор Playwright 1.57–1.65 дал 3 категории (P1 взять, P2 по желанию, НЕ брать — Bun/component testing) и нашёл ловушки (useDefineForClassFields, буферы page.requests()). Руками это ~час чтения, скиллом — минуты.

### 15. secrets-audit
**Что:** перед каждым коммитом сканирует дифф и staged на паттерны секретов (ключи, токены, .env), проверяет .gitignore.
**Зачем:** мы делали этот grep руками перед обоими коммитами (и нашли только упоминание имени `API_KEY` — но проверять надо каждый раз). Дешёвая страховка от утечки ключа в git-историю.

## Отладка

### 16. root-cause-debug
**Что:** дисциплина разбора бага: воспроизведи → минимизируй → найди первопричину (не симптом) → фикс + регрессионный тест → записать почему.
**Зачем:** наш дебаг «аттачи не в отчёте» — образец: сначала неверная гипотеза (смотрели верхний уровень теста), затем выяснилось, что аттачи живут в steps[]. Без процедуры легко остановиться на «перезапустилось — работает».

### 17. ci-failure-triage
**Что:** разбор красного CI: логи + артефакты → классификация (флак / конфиг / код / окружение) → воспроизведение локально → план фикса.
**Зачем:** у вас CI на Docker + Allure + GitHub Pages с тремя джобами — причин красного много, и половина из них не в коде тестов.

## Доки и онбординг

### 18. repo-onboarding (обобщение /init)
**Что:** исследует незнакомый репозиторий (структура, команды, гейты, готчи, конвенции) и создаёт/обновляет AGENTS.md.
**Зачем:** наш /init потребовал сверять факты (алиасы tsconfig, версии, поведение фикстур) — скилл фиксирует этот чек-лист исследования, чтобы ничего не пропустить.

### 19. env-bootstrap
**Что:** генерирует .env.example с комментариями (какая переменная для чего, где читается), проверяет, что проект стартует с чистого клона; помечает легаси-переменные.
**Зачем:** первый пункт нашей кампании улучшений; заодно сразу нашёл легаси `BASE_URL_AUTH`. Полезно и новому человеку, и агенту.

### 20. adr-log
**Что:** фиксирует архитектурные решения в формате «контекст → решение → почему не альтернативы» в память/доки проекта.
**Зачем:** у вас таких решений уже десяток (aria-снапшоты вместо пиксель-диффов, pageWithMonitoring на слушателе вместо page.requests(), allure-playwright запин). Без лога каждое приходится переобосновывать заново.

## С чего начать

Для этого репозитория я бы строил в порядке: **10 (flaky-hunter)** — живой сайт флакает постоянно; **16 (root-cause-debug)** — экономит часы на каждом инциденте; **14 (release-notes-digest)** — следующая версия Playwright не за горами; **11 (regression-on-bug)** — превращает правило из AGENTS.md в исполняемую процедуру.
